### Candidatos a nova regra de contrato
- **Proposta de classe E nova: "Mecanismo de transporte de variável/script de terceiro (ex.: `appleboy/
  ssh-action`/`drone-ssh`) deve ser tratado como caixa-preta não auditável até prova em contrário."**
  Evidência: 3 iterações de fix (PR #23, #24, #25) foram necessárias para identificar a causa raiz real do
  erro de sintaxe em produção. As duas primeiras hipóteses (token em `envs:` malformatado; depois,
  variáveis em geral via `envs:`) eram plausíveis e tecnicamente razoáveis, mas **nenhuma delas era a causa
  real** — confirmado só na 3ª iteração, quando o log mostrou `INPUT_ENVS:` vazio e o erro persistiu, isolando
  a causa no parsing do bloco `script:` multilinha pelo `drone-ssh` em si. Padrão a vigiar: quando uma
  action de terceiro falha de forma opaca (sem expor o comando final montado em texto claro no log),
  resistir à tentação de "corrigir e tentar de novo" sem antes confirmar, com log real, que a hipótese
  anterior foi de fato a causa — declarar explicitamente o que mudou e por que a falha deveria desaparecer,
  e validar isso antes de propor a próxima hipótese. [PENDENTE classe E — só 1 entrega registrada até agora,
  critério de promoção exige 2+ ocorrências; registrar como candidato e monitorar se o padrão se repete em
  outra entrega de CI/infraestrutura.]
- **Proposta de regra para Spec de infraestrutura/CI**: quando a Spec envolve action de terceiro com
  transporte de credencial (token, chave), exigir explicitamente que a revisão confirme onde o valor
  sensível circula em cada etapa do pipeline (env var → output → interpolação em outro step → log) antes de
  aprovar — esta sessão teve um achado real de exposição de token via `GITHUB_OUTPUT` interpolado (PR #25,
  1ª submissão) que só foi detectado por essa auditoria passo-a-passo, não por declaração do Codex nem por
  scanner automatizado (`security-review-agent` não capturou esse padrão).

### Padrões que funcionaram (reforço)
- **Não aceitar "causa raiz" por declaração — sempre puxar o log real do GitHub Actions antes de validar um
  fix.** Nas 3 rodadas de fix, a auditoria buscou e leu o log real de cada run que falhou (via `gh run view
  --log`, decodificando UTF-16LE) antes de avaliar a correção proposta. Isso evitou aprovar prematuramente
  a 1ª e 2ª hipótese de causa raiz, que se mostraram incorretas na prática — só a 3ª, validada por execução
  real pós-merge, resolveu de fato. Reforçar como padrão obrigatório em toda revisão de fix de CI/infra.
- **Bloquear por achado de segurança estrutural, mesmo sem certeza absoluta de exploração.** No PR #25 (1ª
  submissão), o achado de token potencialmente exposto via `GITHUB_OUTPUT` foi bloqueado mesmo sem 100% de
  certeza de que o mascaramento automático do GitHub falharia — o princípio aplicado foi "não há garantia
  documentada de que o mascaramento cobre esse caso, e há alternativa simples e segura disponível" → bloquear
  e pedir correção na origem, não aceitar com ressalva. Codex corrigiu na raiz (removeu o token do payload
  por completo) em vez de tentar provar que o mascaramento funcionaria — resultado mais robusto.
- **Verificação independente de evidência usando GCM quando `gh`/PAT retornam 401.** Reaplicação direta da
  lição já registrada (incidente PP-015, 2026-06-17) — usado em múltiplos pontos desta sessão (fetch de
  branches, `gh workflow run`, `gh run view --log`) sem nenhuma falha. Padrão consolidado e funcionando.
- **Disparo e acompanhamento real do workflow pós-merge, fechando o ciclo de evidência da Spec.** Em vez de
  apenas confiar no relatório do Codex de que "deveria funcionar agora", a revisão disparou o workflow
  real, aguardou conclusão e leu o log de sucesso linha a linha antes de declarar PP-017 encerrado.

### Padrões emergentes observados nesta sessão
- **Entregas de infraestrutura/CI tendem a precisar de mais rodadas de fix do que entregas de código de
  aplicação**, porque a superfície de erro (comportamento de actions de terceiro, parsing de shell remoto)
  não é visível em testes locais nem em `node:test` — só se revela em execução real contra o ambiente de
  produção. Esta entrega teve 1 Spec + 3 PRs de fix subsequentes, todos pequenos e cirúrgicos, mas em série.
  Hipótese de padrão: para esse tipo de entrega, talvez valha estabelecer expectativa explícita já na Spec
  de que "N iterações de ajuste fino pós-merge são esperadas e aceitáveis", para não gerar percepção de que
  a primeira entrega "deveria" ter funcionado de primeira. Confirmado/sinal único: sinal único nesta
  entrega — observar se entregas futuras de CI/infra também precisam de múltiplas rodadas.
- **Action de terceiro (`appleboy/ssh-action`) não expõe o comando shell final montado em texto claro no
  log**, o que tornou a depuração mais lenta do que seria com visibilidade total. Hipótese de padrão: para
  workflows que dependem dessa action, pode valer a pena, desde já, adotar a estratégia final (script como
  arquivo + payload, sem variáveis via `envs:`) como padrão recomendado para *todo* workflow novo do
  projeto que precise enviar lógica complexa via SSH — evita reincidir no mesmo problema em
  `scrape-every-2h.yml` ou futuros workflows, caso algum dia precisem de lógica mais complexa que hoje.
  Confirmado/sinal único: sinal único — `scrape-every-2h.yml` hoje usa `envs:` e nunca falhou com esse
  padrão, então não é uma urgência, apenas uma observação para o caso de precisar de manutenção futura.
